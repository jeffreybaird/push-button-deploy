# Frameworks

[← Docs index](index.md) · push-button-deploy

The four `service` stacks — Phoenix, Sinatra, Rails and Zola — and how each is
generated, tested, built and released.

## At a glance

`FRAMEWORK` picks the service stack the bootstrap generates and deploys. Set it
once, before the first `./bootstrap.sh`, in `.env` or the environment.

| | `phoenix` (default) | `sinatra` | `rails` | `zola` |
|---|---|---|---|---|
| Kind | dynamic app | dynamic app | dynamic app | **static site** |
| Language | Elixir | Ruby 3.3+ | Ruby 3.3+ | Markdown + Tera |
| App | `mix phx.new` (Phoenix 1.8) | `scripts/new-sinatra-app.sh` | `scripts/new-rails-app.sh` | `scripts/new-zola-site.sh` |
| Server | `mix release` (OTP) | Puma (Rack) | Puma (Rails) | none — Caddy serves files |
| Skill docs | `app-template/` | `app-template-ruby/` | `app-template-rails/` | `app-template-zola/` |
| Database | `postgres` or `sqlite` | `sqlite` only (forced) | `sqlite` only (forced) | none (forced) |
| Additional framework tools | `mix` (+ `phx_new` to generate) | `openssl`; no local Ruby | `openssl`; no local Ruby | no local Zola |
| CI gate | `mix test` | `bundle exec rspec` | `bin/check` (RSpec, Cucumber, coverage, RuboCop, audit) | `zola build` |
| Migrations | `Release.migrate()` | `rake db:migrate` | `rails db:prepare` | n/a |
| Container image | built + pushed to DOCR | built + pushed to DOCR | built + pushed to DOCR | **none** |
| Release | blue/green swap | blue/green swap | blue/green swap | symlink flip |

The three dynamic frameworks share the same infra, TLS, blue/green swap, registry
and rollback path — only the app-runtime pieces differ. All stacks need the
shared service tools in [Prerequisites](prerequisites.md), including Python for
agent docs. An existing app with the selected stack's marker skips scaffolding;
bootstrap still prepares release and deployment files and adopts unmanaged docs.

## Phoenix

**Language:** Elixir. **Default framework.**

- **Generated by** `mix phx.new` (Phoenix 1.8), run inline by the bootstrap —
  Phoenix insists on creating the directory itself and needs the database flag,
  so it is not a separate scaffold script. Generating locally needs `mix` plus
  the `phx_new` archive.
- **Server:** an OTP release built with `mix release`.
- **Database:** `postgres` or `sqlite`. Postgres is DigitalOcean Managed
  Postgres (private-VPC, TLS verified); SQLite uses Litestream replication. See
  [Databases](databases.md) for the tradeoffs and conversion caveats.
- **CI gate:** `mix test` with the app's configured database adapter. The workflow
  starts Postgres 17 even when the generated SQLite app does not use it. Red
  tests block the build and deploy.
- **Migrations:** run via the release task `Release.migrate()` **before** traffic
  switches; a failed migration leaves the old release serving.
- **Image and release:** a container image built on amd64 CI and pushed to DO
  Container Registry, SHA-pinned; released by the health-checked blue/green swap.

## Sinatra

**Language:** Ruby 3.3+.

- **Generated by** `scripts/new-sinatra-app.sh` — a modular Sinatra app on Sequel
  with a worked example (a `Note` resource with a service object, a Sequel
  migration, ERB views and an RSpec suite). The scaffold is written in bash and
  the Ruby build runs in Docker/CI, so it works on a machine with no Ruby
  installed; `openssl` generates the secret.
- **Server:** Puma (Rack).
- **Database:** **SQLite only** (forced). Sinatra reuses the whole SQLite path —
  Litestream replication, no managed Postgres. See [Databases](databases.md).
- **CI gate:** `bundle exec rspec` against SQLite.
- **Migrations:** `rake db:migrate` (Sequel), run before traffic switches.
- **Image and release:** a container image built and pushed to DOCR; released by
  the blue/green swap.

Install an existing Sinatra app's agent docs with
`./agent-docs.sh configure <app_dir> --framework sinatra`; use `diff` and `update`
for later shared updates.

## Rails

**Language:** Ruby 3.3+. Select Rails explicitly:

```bash
FRAMEWORK=rails ./bootstrap.sh ~/src/myapp
# Or scaffold locally, without provisioning:
./scripts/new-rails-app.sh ~/src/myapp
```

- **Generated by** `scripts/new-rails-app.sh`, a Bash scaffold for a minimal
  Rails 8.1 application (default Ruby 3.3.12 and Rails 8.1.4 or later in the
  8.1 series). It needs no local Ruby installation. The starter uses
  Active Record and Action Controller, with a working health endpoint and a
  server-rendered Notes example. Domain services return explicit Results; lists
  paginate, archived notes remain in storage, and mutations carry audit records.
- **Server:** Puma binds `0.0.0.0:$PORT` (port 4000). Caddy terminates HTTPS;
  the container health check requires HTTP 200 from `/health` over internal
  HTTP, without an HTTPS redirect.
- **Database:** one SQLite database at `/data/app.db` in production, persisted
  and replicated through the existing Litestream path. The starter does not
  enable Solid Queue, Solid Cache or Solid Cable, which would need additional
  databases and deployment configuration.
- **CI gate:** `bin/check` runs RuboCop, RSpec, strict Cucumber acceptance
  features, merged SimpleCov coverage and a current dependency audit before
  the image build. Coverage requires 100% lines and 100% branches and
  includes application files that tests never load.
  Both GitHub and Gitea receive deployment and rollback workflows; GitHub also
  supports the shared PR staging slot.
- **Migrations:** `bundle exec rails db:prepare` runs before the blue/green
  swap. A failed migration leaves the previous release serving. Rollback changes
  the image only and does not reverse migrations.

`--service ruby` continues to select Sinatra. Use `FRAMEWORK=rails` to select
Rails, including when `LANGUAGE=ruby` is also set.

An existing Rails application is identified by `config/application.rb`, rather
than a generic `Gemfile`. Bootstrap preserves application code and installs the
selected deployment files and managed agent documentation. Existing apps must
be compatible with the single SQLite database, production database path,
`SECRET_KEY_BASE` and health-check conventions described above. Bootstrap does
not convert adapters, move existing data, configure encrypted credentials, or
add storage and workers for additional services. Review those requirements
before deploying an existing application. Keep `config/puma.rb` compatible with
the bind and port above. Apps needing Node, a JavaScript bundler, native packages
or additional asset build steps need an appropriate Dockerfile build setup; the
minimal starter does not install those toolchains.

The starter includes Rails-specific guidance for service boundaries, Active Record,
SQLite, authorization and request scope, testing, observability, accessibility,
and CSS design tokens. Optional integration guidance describes how to add a
capability when needed; it does not provision authentication, queues, billing or
external services.

Install Rails agent guidance independently with
`./agent-docs.sh configure <app_dir> --framework rails`. Guidance updates do not
install gems or rewrite existing application code. For compatibility, deployment
workflows use the existing `rails db:prepare` and `rails test` gate when an adopted
application has no `bin/check`, and log that choice. If `bin/check` exists, it must
run successfully; a failure or missing executable permission never falls back to
the legacy gate. Adopting the new tooling in an existing app requires adding its
dependencies, configuration, suites and executable check script deliberately.

## Zola

**Language:** Markdown + Tera templates. `FRAMEWORK=zola` deploys a **static
site**, which changes the *shape* of the deploy rather than just its language:

```bash
FRAMEWORK=zola ./bootstrap.sh --host ~/src/myapp ~/src/myblog
```

- **Generated by** `scripts/new-zola-site.sh` — a themeless starter. The build
  runs in CI, so no local Zola installation is required.
- **Server:** none. The shared, host-owned Caddy serves the built files directly
  — `/root/apps` is bind-mounted into it at `/srv`.
- **Database:** none (forced). No secrets, and no `.env` on the droplet —
  nothing a static site ships is secret.
- **CI gate:** `zola build` is the whole gate. A bad template, unparsable front
  matter or a broken internal `@/` link fails the build, and nothing is uploaded
  — the live site keeps serving.
- **No container, no image, no registry repository.** CI runs `zola build`, tars
  `public/`, and ships it to `/root/apps/<slug>/releases/<sha>` on the droplet.
- **Release is one atomic symlink move.** `publish.sh` points `current` at the
  new release with a single `rename(2)`. Caddy resolves the document root per
  request, so there is no reload, no restart and no swap window.
- **Rollback re-points the symlink** — old releases stay on disk (5 by default,
  `KEEP_RELEASES` in `publish.sh`), so nothing is rebuilt or re-uploaded. Past
  that window, re-deploy the commit instead.
- **Zola is pinned in `.zola-version`**, read by CI. Themes work the standard way
  (git submodules; the checkout is recursive).

Because a static site pushes no image, it is the cheapest thing to put on a
droplet that already serves something else — it consumes a directory and a Caddy
site file, and nothing at runtime. It also sidesteps the container registry
entirely, which matters on the free starter tier (one repository per account).
Install an existing Zola site's agent docs with
`./agent-docs.sh configure <site_dir> --framework zola`.
